# 密钥平台与套餐授权原子保存

## 决策

- API Key 的平台授权和订阅套餐授权是两组独立、多选的资产权限，保存时必须同时保留。
- 更新授权时，允许明确清空其中一组，但不得因为保存另一组而隐式清空未变化的关联。
- `api_key_platforms` 与 `api_key_subscription_plans` 的更新必须保持在同一条原子数据库操作中。

## 根因

旧的 `ReplaceAssetPermissions` 使用多个数据修改 CTE 先删除全部关联、再插入新关联。PostgreSQL 不保证同一条语句中兄弟数据修改 CTE 的执行顺序；插入可能先遇到旧关联的唯一键冲突，随后删除又把旧关联删掉，结果表现为平台和套餐交替丢失。

## 正确实现

- 以目标 API Key 行作为稳定目标集并加行锁。
- 插入目标集合中缺少的关联。
- 只删除不在目标集合中的旧关联，避免删除与插入之间的顺序依赖。
- 同时更新 `allow_balance`，并保留显式传入的空数组语义。

相关代码：`backend/internal/repository/api_key_repo.go` 的 `ReplaceAssetPermissions`。

## 验证

- 仓储 SQL 单测覆盖目标集合删除、幂等插入和参数归一化。
- 服务层授权更新测试通过。
- 前端 `KeysView` 编辑测试覆盖平台与套餐同时选择并提交。
- 在 PostgreSQL 18 测试数据库中回放四种组合：两者都有、仅平台、仅套餐、都清空；结果均与目标集合一致。

## 后续同步约束

同步官方代码或重做 API Key 权限时，必须保留平台与套餐双数组的提交契约，以及上述“按目标集合差异更新”的数据库语义；不得恢复“删除全部后再插入”的兄弟数据修改 CTE 写法。
