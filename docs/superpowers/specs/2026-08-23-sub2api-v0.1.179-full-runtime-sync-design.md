# Sub2API v0.1.179 全量 Runtime 同步设计

- 状态：已确认
- 日期：2026-08-23
- 官方基线：`v0.1.179@75f88be5f75c27771836b586f7de1503afa0e3bc`
- 同步目标：在保留 XCode ProductCore 的前提下，实现 Sub2API `v0.1.179` 的完整 Runtime 功能等价

## 背景与事实基线

XCode 当前内嵌 Runtime 源自 Sub2API `0.1.169`，并已加入 RuntimeBridge、平台、模型广场、套餐、API Key、计费和前端等自定义能力。当前 `main` 已选择性移植一个官方 Responses/Chat 兼容修复，但尚未完整同步官方 `v0.1.179`。

官方正式版固定为 Tag `v0.1.179`，对应提交 `75f88be5f75c27771836b586f7de1503afa0e3bc`。该 Tag 源码中的 `backend/cmd/server/VERSION` 仍为 `0.1.178`，因此同步身份以 Git Tag 和完整 commit SHA 为准，不以该版本文件为准。

从官方 `v0.1.169` 到 `v0.1.179` 共有 594 个提交。XCode 与官方代码树已经分叉：Service、Handler、Repository、Ent schema、迁移、配置和前端均存在大量差异，不能通过整体 merge、文件覆盖或直接执行官方迁移安全完成升级。

## 目标

1. 让 XCode 具备 Sub2API `v0.1.179` 的全部 Runtime 能力，包括协议、Provider、账号池、OAuth、额度、调度、冷却、重试、失败切换、流式、WebSocket、媒体和扩展端点。
2. 保留 XCode 对平台、模型目录、模型价格、套餐、余额、API Key、订单、计费、用量归属和产品前端的所有权。
3. 新同步的 Provider 和端点默认不自动创建平台、不自动启用账号、不改变现有生产流量；管理员配置对应平台和 AI 账号后才生效。
4. 建立可重复的官方版本同步流程，使后续升级以官方版本差异和少量 XCode 边界适配为主。

## 非目标

- 不把 XCode 恢复成官方 Sub2API 产品。
- 不恢复 XCode 已移除的 Group/Channel 产品模型。
- 不覆盖 XCode 前端、套餐、余额、API Key、支付、订单或模型广场。
- 不自动修改香港生产配置、平台状态或账号状态。
- 不在本阶段直接发布 Tag、生成生产离线包或升级香港服务器。

## 架构边界

### 官方 Runtime 核心

同步协议转换、Provider 实现、OAuth、AI 账号运行状态、额度查询、调度、冷却、重试、失败切换、HTTP/SSE/WebSocket、图片、视频、音频、Live、Search 和 Composite 等执行能力。同步代码尽量保留官方目录、文件名、函数结构和测试语义，避免在官方核心算法内混入 ProductCore 判断。

### XCode ProductCore

继续唯一拥有用户账号、平台授权、模型目录、价格、套餐、余额、API Key、支付、订单、用量入账和扣费语义。官方 Group、Channel 和定价逻辑只能作为 Runtime 能力或价格事实的参考，不能绕过 ProductCore 直接决定用户资产或扣费。

### RuntimeBridge 适配层

所有生产请求继续遵循：

```text
ApplicationGateway -> RuntimeBridge v1 -> Local Port -> Sub2API Driver -> Provider
```

XCode 差异集中在 Driver、Port、Adapter 和配置映射中。公开 Handler 和 ProductCore 不接触官方 Runtime 内部类型；Runtime 只上报账号、端点、模型、token、缓存、媒体、时延和终态等事实。

### 共享状态与配置

账号协议、多协议 Base URL、Header 覆写、代理探测目标、Provider 额度快照、OAuth 凭据和运行状态通过 XCode 账号/平台配置提供。优先复用现有 `accounts.extra`、平台 Runtime 配置和 usage 字段；只有需要数据库查询、唯一性或完整性约束时才新增结构化字段。

## 功能归宿规则

官方 `v0.1.179` 的每项功能必须进入功能矩阵并归入以下一种状态：

1. `direct_sync`：纯 Runtime 功能，可按官方结构同步。
2. `adapter_port`：Runtime 功能需要通过 RuntimeBridge 或 XCode 配置适配。
3. `xcode_equivalent`：XCode 已有功能等价实现，保留 XCode 实现并补充对照测试。
4. `productcore_mapping`：官方功能依赖 Group/Channel/计费模型，映射到 XCode 平台、模型价格或资产语义。
5. `not_runtime`：官方纯产品或营销功能，不进入 Runtime 同步范围，但必须记录排除理由。

“全部 Runtime 功能”以功能等价为验收标准，不要求 XCode 文件树与官方仓库逐文件相同。

## 同步阶段

### 阶段一：官方基线与功能矩阵

- 固定官方源码快照、Tag、commit SHA 和文件哈希。
- 分类 `v0.1.169...v0.1.179` 的 594 个提交和 Release Notes。
- 为每项功能记录官方提交、相关文件、XCode 当前路径、归宿状态、数据库影响、测试和完成状态。
- 建立官方文件清单、XCode 覆盖清单和边界适配清单。

### 阶段二：纯 Runtime 与协议核心

- 同步 Chat Completions、Responses、Messages 和协议互转。
- 同步 reasoning、工具调用、输入 token 预检、容量错误识别和非流式读取失败切换。
- 同步 HTTP Bridge replay、WebSocket 多轮状态、客户端工具映射和终态校验。
- 保持 RuntimeBridge v1 公开 contract 不变；确需扩展时单独提出 contract 变更审查。

### 阶段三：账号池与 Provider

- 同步 OpenAI/Codex、Grok、Gemini、Antigravity、Kimi、Zhipu GLM、DeepSeek、Ollama 等 Provider 能力。
- 同步 OAuth/API Key、自适应 API 协议、多协议 Base URL、Header 覆写、额度/余额查询和账号测试。
- 同步账号选择、亲和性、运行状态、冷却、同账号重试、账号间切换和容量/鉴权错误处理。
- 确保只有 Runtime 管理 AI 账号；ProductCore 管理用户账号和授权，两类账号语义不得混合。

### 阶段四：媒体与扩展端点

- 同步图片、视频、音频、Live、Alpha Search、原生 Search、Responses input tokens 和 Composite Runtime 路由。
- 媒体异步任务的 Provider 状态由 Runtime 管理，用户授权和最终扣费由 ProductCore 管理。
- 所有成功终态通过 RuntimeBridge 上报可审计 usage facts；失败终态不得伪造成功 usage。

### 阶段五：Runtime 管理配置

- 在 XCode 现有平台和账号后台补齐 Runtime 必需配置。
- 新 Provider、新端点和新能力在代码层可用，但默认未配置、未启用。
- 管理接口返回运行状态和额度事实，不暴露凭据，不复制官方 Group/Channel 产品配置。
- 前端只实现这些 Runtime 配置的必要管理界面，不覆盖 XCode 产品导航和资产交互。

### 阶段六：数据库、全量回归与发布验收

- 完成 Runtime 必需数据库适配、存量数据升级和回滚验证。
- 运行后端、前端、架构、迁移、PostgreSQL、Docker 和安全门禁。
- 在一次性环境中配置各 Provider，验证请求、切换、usage 和扣费归属。
- 临时环境全部通过后，另行确认发布、离线包和香港生产升级。

## 数据库策略

1. 不直接执行官方 migration `217-228`，不复用其编号。
2. XCode 已发布 migration checksum 保持不变；Runtime 同步迁移使用预留的 `8000-8999` 区间。
3. 不恢复 Group、Channel、旧授权表或已删除的产品字段。
4. 官方迁移中的 Runtime 需求必须先拆分：仅将 Provider、账号运行状态、协议配置和 usage facts 所需部分翻译为 XCode 增量迁移。
5. 官方渠道定价、长上下文倍率和计费默认值不直接进入 Runtime。价格和扣费仍由 XCode ProductCore 决定。
6. 每个迁移必须包含：存量数据兼容测试、重复执行保护、失败可见性、升级前后计数对账和数据库恢复演练步骤。
7. 不为方便同步新增双写、静默 fallback 或第二套账号/计费数据模型。

## 错误与计费语义

- Runtime 成功终态发布 `usage_final`，包含实际账号、上游模型、端点、token、缓存、媒体、时延和终态事实。
- Runtime 失败终态发布 `runtime_failed`；即使上游返回部分 usage，也不得被误判为成功请求或重复扣费。
- 流式内容一旦写给客户端，失败切换必须遵守现有 `SafeToFailoverAfterWrite` 约束，禁止拼接两个账号的响应。
- ProductCore 根据成功 usage facts 和冻结的产品决策完成套餐/余额扣费；Runtime 不直接写用户余额或套餐用量。
- 未配置 Provider 返回明确的不可用/无账号错误，不得影响已启用平台。

## 测试与验收

### 自动化门禁

- 官方功能矩阵无未分类项。
- 每批同步包含官方对应测试或 XCode 等价回归测试，并验证测试在修复前能失败。
- RuntimeBridge contract、架构守卫、Service、Handler、Repository、migration 和 PostgreSQL 集成测试通过。
- 前端单测、typecheck、lint、production build 和依赖审计通过。
- `go build ./cmd/server`、Docker 离线镜像构建和镜像启动健康检查通过。

### 行为验收

- GPT/Codex 的 Chat、Responses、SSE、工具调用、reasoning、账号重试和故障切换全部通过。
- 每个已配置 Provider 至少完成其支持协议和额度/状态查询验收；无法取得真实账号时保留为明确阻塞，不伪造通过。
- 图片、视频、音频、Live、Search、WebSocket 和 Composite 按支持矩阵完成成功与失败终态验证。
- 未配置 Provider 不自动创建平台、不接收流量、不改变现有平台选择。

### 数据与财产验收

- 升级前后用户、API Key、平台、AI 账号、套餐、订阅、余额、订单和历史 usage 数量及关键金额对账一致。
- 成功 usage 的平台、AI 账号、套餐/余额来源、`total_cost` 和 `actual_cost` 符合 XCode 规则。
- 失败请求不写成功 usage、不增加套餐用量、不扣余额。
- 数据库恢复演练能够回到升级前状态。

## 提交与发布纪律

- 所有工作在独立 worktree 和专用分支中进行。
- 每个阶段按可回滚单元提交；共享 contract、schema、依赖、根配置和 CI 变更串行审查。
- 不执行 `merge upstream/main`、`reset --hard` 或官方文件树整体覆盖。
- 阶段完成只表示本地实现和门禁通过，不等于已发布。
- 推送、Tag、Release、离线包上传和香港部署必须单独获得确认。

## 后续同步方式

后续官方升级遵循：

```text
旧官方 Tag..新官方 Tag
  -> 提交与文件自动分类
  -> 更新功能矩阵
  -> 同步官方 Runtime 核心
  -> 重放少量 XCode Adapter/Port 适配
  -> 数据库影响审查
  -> 自动化与真实 Provider 验收
```

官方核心与 XCode 产品逻辑的边界越集中，后续升级越接近版本差异同步，而不是重新人工移植整个仓库。

## 完成定义

只有同时满足以下条件，才可声明 XCode 已完整同步 Sub2API `v0.1.179` Runtime：

1. 功能矩阵中所有 Runtime 项均为已实现、XCode 等价或有真实外部账号阻塞记录。
2. Release Notes 中所有 Runtime 新增、优化、Bug 修复和破坏性变更均有明确处理结果。
3. 自动化门禁、数据库兼容检查和可执行的 Provider 验收完成。
4. XCode ProductCore、RuntimeBridge 所有权、计费语义和现有生产数据未被破坏。
5. 新 Provider 默认未配置、未启用，现有生产流量行为保持不变。
