# API Key 统一套餐授权与注册默认 Key 设计

- 状态：已确认，待实现
- 日期：2026-08-22
- 范围：API Key 权限模型、计费解析、注册初始化和前端授权表单

## 背景

当前 API Key 将套餐授权保存为 `subscription_plan_ids` 数组。数组为空时表示“不允许套餐，只能使用余额”，因此不能把空数组重新解释成“允许全部套餐”。同时，创建 Key 需要调用方显式提交平台和套餐列表，注册流程也没有统一、幂等的默认 Key 初始化。

本次把套餐授权收敛为两个业务开关：允许套餐、允许余额。平台仍使用当前实际平台 ID，平台授权和套餐授权保持不同的生命周期语义。

## 目标

1. 新建 API Key 默认授权当前所有可用平台、所有套餐和余额。
2. 编辑已有 Key 时保留原有平台授权；新增平台不自动加入已有 Key。
3. 套餐开关开启后，允许用户当前已有及未来购买的所有套餐，无需修改 Key。
4. 迁移历史 Key 时，保留“仅余额”与“套餐授权”之间的权限差异。
5. 邮箱和全部 OAuth 注册路径都自动创建一个默认 Key。
6. 默认 Key 创建具备幂等性；创建失败不阻断注册，首次登录时可补建。
7. 缓存、API、前端和数据库迁移在滚动发布期间保持兼容。

## 非目标

- 不新增“全部平台”伪选项；平台授权始终是具体平台 ID，例如 Codex、GLM、DeepSeek。
- 不让已有 Key 自动获得未来新增平台。
- 不把所有套餐 ID 动态展开写入每个 Key。
- 不改变用户账号与 Runtime AI 账号的职责边界。
- 不修改订阅购买、余额扣费、平台路由和账号池调度规则。
- 不删除历史字段或重写不可变的 `001-200` 发布迁移。

## 权限模型

### 持久化字段

在 `api_keys` 增加一个布尔字段：

- `allow_all_subscriptions`：默认 `false`；为 `true` 时表示该 Key 可使用用户所有有效套餐，包括未来购买的套餐。

保留现有 `allow_balance` 字段。旧的 `api_key_subscription_plans` 关联表和 `allowed_subscription_plan_ids` 读取兼容逻辑在迁移完成后不再作为新业务输入，但关联数据需要清理，避免产生两套权威。

平台关联表继续保存具体平台 ID。创建时取当前可用平台快照；更新时只有显式提交平台列表才替换关联。

### 请求契约

创建和更新 API 使用业务字段：

- `platform_ids`：具体平台 ID 数组；创建时缺省表示当前全部可用平台，更新时缺省表示不变。
- `allow_all_subscriptions`：是否允许所有套餐；创建默认 `true`，更新缺省表示不变。
- `allow_balance`：是否允许余额；创建默认 `true`，更新缺省表示不变。

新接口不再要求前端按套餐逐项提交。为滚动发布兼容，后端短期可读取旧的 `subscription_plan_ids` 输入，但新写入只维护 `allow_all_subscriptions` 和 `allow_balance`；旧字段与新字段同时出现时以新业务字段为准。

Key 至少需要一个平台，且至少开启套餐或余额之一。创建默认值满足这两个约束；显式关闭两者时仍返回原有校验错误。

## 历史数据迁移

新增 ProductCore migration 使用 `9000` 段，执行顺序如下：

1. `ALTER TABLE api_keys ADD COLUMN allow_all_subscriptions BOOLEAN NOT NULL DEFAULT FALSE`。
2. 对仍存在有效套餐关联的 Key，将 `allow_all_subscriptions` 更新为 `TRUE`。
3. 清空旧的逐套餐关联记录，使新字段成为唯一套餐授权来源。
4. 保留原本没有套餐关联、但 `allow_balance = true` 的 Key 为“仅余额”；不因迁移扩大权限。
5. 为迁移编写可重复执行的测试，验证默认值、回填和关联清理。

迁移只增加一列并清理一张关联表，不改变用户、订阅、用量和计费流水数据。回滚策略是应用先停止读取新字段，再恢复旧关联快照；正式迁移前需要执行数据库备份。

## 请求计费解析

平台路由成功后，`ResolveBillingAssetForRequest` 按以下顺序解析：

1. `allow_all_subscriptions = true` 时，查询该用户全部有效订阅，按现有到期时间、创建时间和 ID 的稳定顺序选择首个可用套餐，并复用现有额度窗口维护和失败候选跳过逻辑。
2. 兼容窗口内，如果 Key 仍带旧套餐 ID 且新字段为 `false`，只允许这些具体套餐；迁移完成后新数据不再走此分支。
3. 套餐没有可用候选时，若 `allow_balance = true` 且余额充足，则回退余额；否则返回现有 `NO_USABLE_BILLING_SOURCE` 或余额不足错误。

“全部套餐”查询必须使用用户订阅列表能力，不在 Key 上展开套餐 ID。这样新购买套餐会立即生效，也避免套餐同步和并发更新时写放大。

## API Key 创建与更新

### 创建

- APIKeyService 获取当前可用平台列表，并在请求未提供 `platform_ids` 时填充全部平台 ID。
- 默认 `allow_all_subscriptions=true`、`allow_balance=true`。
- 创建 Key 与平台关联、新字段写入、旧套餐关联清理应在同一业务操作中完成；失败时不返回半成品 Key。

### 更新

- 平台列表只有在请求显式传入时才替换，已有 Key 不跟随平台新增自动扩权。
- 套餐表单只修改 `allow_all_subscriptions`；不再向每个套餐写关联。
- 余额开关独立修改。
- 任何权限字段变化后，必须使 API Key L1/L2 认证缓存失效，并发布跨实例失效消息。

## 注册默认 Key

在 `postAuthUserBootstrap` 统一接入窄接口 `DefaultAPIKeyProvisioner`，由 AuthService 依赖接口而不是具体 APIKeyService，避免服务包循环依赖。所有邮箱和 OAuth 用户创建路径都继续调用这个统一钩子，覆盖 Google、GitHub、LinuxDo、微信、钉钉、OIDC 等现有入口。

默认 Key 参数：

- 名称：系统固定的本地化默认名称；
- 平台：创建瞬间当前全部可用平台；
- 套餐：`allow_all_subscriptions=true`；
- 余额：`allow_balance=true`。

幂等规则：按用户查询是否已有有效 Key；已有任意 Key 时不重复创建。并发注册或重复回调由数据库唯一约束/事务冲突处理保证最多一个默认 Key。

失败语义：默认 Key 创建失败只记录结构化日志，不阻断注册或 OAuth 回调；首次成功登录时再次尝试补建。补建仍遵循同一幂等规则，避免重复 Key。

## 前端交互

`KeyAssetPermissionsForm` 改为两组区域：

- 平台：展示当前所有具体平台，创建时默认全选；编辑时显示并保留已有选择。
- 计费：仅显示“允许套餐”和“允许余额”两个开关；创建页默认都开启。

不显示“全部平台”选项，也不展示逐套餐复选框。API 类型、国际化文案、创建/编辑回显和表单测试同步更新。新增平台在创建新 Key 时自动出现在全选集合中，旧 Key 编辑不会被隐式修改。

## 缓存与兼容发布

认证缓存快照需要包含 `allow_all_subscriptions`。旧缓存条目缺少该字段时按 `false` 处理，并在权限读取或发布时自然刷新。权限更新、迁移后批量权限变化都要触发按 Key 或按用户的缓存失效；跨实例通过现有 Pub/Sub 通道传播。

发布顺序：先发布包含新列读取兼容和默认值的后端，再执行 migration，再发布前端和仅发送新字段的客户端。旧后端在新列存在时仍可运行，旧前端提交的套餐 ID 在兼容窗口内不会被拒绝。

## 测试策略

后端：

- 权限规范化与校验：创建默认值、显式关闭、平台必选、套餐/余额至少一个。
- Resolver：全部套餐查询、未来套餐可用、候选耗尽后余额回退、旧字段兼容。
- Repository/Ent：新字段读写、缓存快照序列化和反序列化。
- Migration：旧套餐 Key 回填为全部套餐、纯余额 Key 不扩大权限、旧关联清理、重复执行安全。
- 注册：邮箱和每个 OAuth 入口调用默认 Key provisioner；失败不阻断；首次登录补建；并发幂等。

前端：

- 创建默认全平台、套餐和余额；
- 编辑保留已有平台；
- 只渲染两个计费开关；
- 新增平台不改变已有表单初始值；
- API 请求字段和回显字段与后端契约一致。

验证命令按仓库现有门禁执行：Go 定向单元测试和 migration 测试、前端 Key 组件测试、`git diff --check`，再运行完整相关包测试。

## 数据库影响与后续演进

本次数据库变更是一个新增布尔列、一次历史关联回填和一次关联清理；用户、订阅、余额、用量日志和 API Key 主记录不重建。后续新增套餐不需要数据库迁移，也不需要批量更新 API Key，只需订阅同步写入用户订阅数据。只有未来改变 Key 权限语义或删除兼容字段时才需要新的显式 migration，并应单独评审。

## 验收标准

- 新建 Key 默认勾选当前全部具体平台，允许所有套餐和余额。
- 编辑已有 Key 不自动加入新平台。
- 历史套餐 Key 迁移后可使用现有及未来套餐；纯余额 Key 仍不能使用套餐。
- 新购买套餐无需更新 Key 即可成功计费。
- 全部注册路径最多自动创建一个默认 Key；创建失败不阻断注册，首次登录可补建。
- 权限更新和迁移后的认证缓存不会继续使用旧授权。
- 迁移测试、后端定向测试、前端 Key 测试和 `git diff --check` 全部通过。
