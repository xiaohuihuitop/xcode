# 平台统一模型权威设计

- 状态：已确认，待实施计划
- 日期：2026-08-07
- 目标分支：`my2.0`
- 兼容策略：保留当前 Platform、账号和授权数据；停止读取账号级模型配置

## 背景

当前 my2.0 已将 Platform 收口为唯一业务路由入口，但模型配置仍存在两套来源：

- Platform 的 `model_rules` 保存请求模型、上游模型和逐模型端点能力。
- Account 的 `credentials.model_mapping` 同时承担账号白名单和账号级模型映射，并在调度阶段过滤账号。
- `/v1/models` 仍从账号 `model_mapping` 聚合模型，未完全服从 API Key 的平台授权。

这导致管理员在添加每个账号时重复配置相同模型，并可能出现平台允许模型但账号过滤模型、模型列表与实际路由不一致等问题。

## 目标

Platform 成为模型白名单、模型映射和端点能力的唯一管理员配置来源。账号只保存凭证、所属平台和调度属性，不再配置模型。

同一 Platform 下的账号被视为能力相同。系统不读取上游模型列表验证账号能力，也不在账号加入平台时做能力校验；管理员负责把能力不同的账号拆分到不同 Platform。

## 已确认决策

1. 采用“平台直接参与运行时调度”，不把平台模型复制到账号，也不保存账号隐藏快照。
2. 端点能力属于 Platform，所有模型共享同一组端点能力。
3. 平台模型配置同时支持白名单和模型映射。
4. 账号创建、编辑和批量编辑不再显示或提交普通模型白名单与模型映射。
5. 账号加入 Platform 时不自动同步、不探测也不校验上游模型。
6. `/v1/models` 只根据 API Key 已授权的 Platform 返回模型。
7. Sub2API 现有负载均衡、OAuth 刷新、协议适配和失败切换继续保留。

## 职责边界

| 概念 | 负责 | 不负责 |
| --- | --- | --- |
| `Platform` | 业务路由、统一端点、模型白名单、模型映射、账号集合 | 用户资产、账号凭证、上游能力探测 |
| `PlatformModelRule` | 请求模型模式与上游模型的映射 | 逐模型端点、账号授权、计费倍率 |
| `Account` | 凭证、平台归属、状态、并发、优先级、代理和调度统计 | 管理员模型白名单、管理员模型映射 |
| `Adapter` | OAuth、协议转换、内置技术别名和上游请求 | 业务平台模型授权 |
| `APIKey` | 授权可使用的平台、套餐和余额 | 定义平台模型能力 |

## 数据模型

### Platform

Platform 增加统一的 `endpoint_capabilities` 字段：

- 使用 JSON 数组保存标准化端点枚举。
- 当前至少支持 `chat_completions` 和 `responses`。
- 启用平台时必须至少选择一个端点。
- 所有启用模型共同使用该字段，不提供逐模型覆盖。

### PlatformModelRule

模型规则继续保存：

- `model_pattern`：客户端请求模型，支持精确名称和单个末尾通配符。
- `upstream_model`：发送给上游的模型；白名单模型与请求模型相同。
- `status`：存储层保留的规则状态；平台表单只维护启用模型，管理员从列表删除模型即取消该规则。

现有 `endpoint_capabilities` 从模型规则迁移到 Platform 后退出运行时读取。本轮保留数据库旧列用于回滚，但从 Ent 活动模型和运行时读取路径移除；物理删除另立清理迁移。

### Account

- 新建、编辑和批量编辑不再写入普通 `credentials.model_mapping`。
- 旧账号中残留的 `credentials.model_mapping` 暂不删除，但新路由不读取它。
- 不将 Platform 模型复制为账号字段或账号缓存快照。
- `compact_model_mapping` 等协议专项配置不自动并入本次普通模型配置；只有确认属于平台公共能力后才另立设计上移。

## 模型配置语义

### 白名单

白名单模型 `gpt-5.6` 等价于：

```text
gpt-5.6 -> gpt-5.6
```

### 模型映射

映射 `gpt-latest -> gpt-5.6` 表示：

- 客户端通过 `/v1/models` 看到 `gpt-latest`。
- 客户端请求 `gpt-latest`。
- GatewayRuntime 向上游发送 `gpt-5.6`。
- 使用记录分别保存请求模型和上游模型。

同一个 `model_pattern` 在同一 Platform 内只能有一条启用规则。新增映射时替换同名自映射，不能生成两个来源互相覆盖。

### 匹配优先级

- 精确模型优先于通配符。
- 通配符只允许出现在末尾。
- 多个通配符匹配时，前缀更长者优先。
- 同一 API Key 授权范围内仍存在同优先级多 Platform 候选时，配置保存失败；运行时继续保留歧义保护。

## 管理界面

### Platform 表单

平台表单包含：

1. 名称、编码、协议适配器和状态。
2. 平台统一端点选择。
3. 模型白名单选择器。
4. 模型映射编辑器。

模型选择交互复用当前账号表单能力：搜索、平台预设、批量填充、清空、自定义模型和模型图标。组件应抽取为平台与通用模型配置可使用的组件，文案不能继续绑定“账号模型白名单”。

平台已有账号后仍禁止修改协议适配器；模型和统一端点允许修改，保存后立即影响该平台全部账号。

### Account 表单

- 创建、编辑和批量编辑页面删除普通“模型白名单”和“模型映射”。
- 账号只选择所属 Platform。
- 页面提示该账号继承 Platform 的模型和端点配置。
- 不提供账号级覆盖入口。

## 请求数据流

1. 验证 API Key，读取它授权的启用 Platform。
2. 根据请求路径标准化当前端点。
3. 在授权 Platform 的启用模型规则中匹配请求模型。
4. 过滤不支持当前端点的 Platform。
5. 按精确/通配符优先级得到唯一 Platform 和上游模型。
6. 仅从该 Platform 的 `platform_id` 账号池选择可调度账号。
7. 不调用账号 `model_mapping` 判断模型支持，也不使用它覆盖上游模型。
8. GatewayRuntime 继续处理负载均衡、粘性会话、并发、OAuth 刷新、限流和失败切换。
9. 计费继续独立选择套餐或余额，保存实际 Platform、账号、请求模型、上游模型和资产归属。

## 特殊适配器

Antigravity、Grok、Bedrock 等适配器可能包含协议实现所需的内置模型别名或格式转换。这些转换属于 Adapter，不属于账号管理员白名单。

实施时必须区分：

- 删除账号可编辑的普通模型配置。
- 保留协议正常运行必需的内置映射和规范化逻辑。
- 旧账号管理员映射在平台路由中始终不执行。
- Platform 的 `upstream_model` 表示上游语义模型；Adapter 只能进行协议必需的格式化或内置规范化，不能改成另一个管理员可配置模型，也不能扩大 API Key 未授权的 Platform 模型范围。

## `/v1/models`

- 只读取当前 API Key 已授权且启用的 Platform。
- 返回这些 Platform 的启用精确请求模型并集。
- 映射规则展示 `model_pattern`，不暴露 `upstream_model`。
- 通配符规则允许直接请求，但不把 `gpt-*` 作为具体模型返回。
- 不再读取 Group、账号 `model_mapping` 或默认账号模型列表兜底。
- Platform 模型、状态、端点或 API Key 平台授权变化后，相关模型列表缓存必须立即失效。

## 错误处理

- API Key 没有匹配的授权 Platform：拒绝请求。
- 授权 Platform 没有请求模型：返回 `model_not_found`。
- 模型存在但 Platform 不支持当前端点：返回 `endpoint_not_supported`。
- 过滤后仍存在同优先级多 Platform：返回平台配置冲突。
- Platform 没有可调度账号：返回服务暂不可用。
- 上游认证、限流、网络或临时错误：沿用现有账号失败切换。
- 上游返回模型不支持：可以沿用现有机制尝试同 Platform 其他账号，但不自动修改 Platform 配置；最终失败由管理员修正账号池一致性。

## 迁移策略

1. 保留当前 Platform、账号、API Key 平台授权和模型规则。
2. 为 Platform 增加统一端点字段。
3. 现有 Platform 的统一端点取其所有启用模型规则端点能力的并集。
4. 运行时切换后停止读取逐模型端点字段；数据库旧列本轮保留但不再写入或读取。
5. 旧账号 `credentials.model_mapping` 保留但停止读取，不做破坏性清理。
6. 不修改用户、余额、套餐、订阅实例、支付审计和历史使用记录。

如果旧 Platform 的部分模型只支持 Chat、部分只支持 Responses，迁移后会按端点并集对该 Platform 全部模型统一开放。这是平台统一端点决策的预期行为。

## 缓存与一致性

- Platform 模型解析不能长期持有未失效的账号模型快照。
- Platform 保存成功后必须失效平台解析和 `/v1/models` 缓存。
- API Key 平台授权变化后必须失效该 Key 的模型列表缓存。
- 同一 Platform 的模型和端点应在一次事务中保存，不能出现规则已更新但端点仍为旧值的中间状态。

## 实施阶段

### 阶段一：数据结构与平台 API

- 增加 Platform 统一端点字段和迁移。
- 调整 Platform 创建、更新、读取及验证。
- 保持模型规则唯一性和跨 Platform 歧义检查。

### 阶段二：运行时

- 平台规则成为唯一模型权限与映射来源。
- 账号池只按 `platform_id` 和调度状态筛选。
- 切断账号 `model_mapping` 对平台路由的过滤和覆盖。
- 重写 `/v1/models` 的授权范围和缓存失效。

### 阶段三：前端

- 将模型白名单与映射交互迁入 Platform 表单。
- 增加平台统一端点设置。
- 从账号创建、编辑和批量编辑移除普通模型配置。

### 阶段四：回归与部署

- 完成后端、前端和 repository 回归。
- 生成 my2 测试镜像并部署腾讯云测试环境。
- 使用临时 Key 验证模型列表、两个 OpenAI 端点、失败切换和实际扣费。

## 验证范围

### 后端

- Platform 统一端点必选、保存和回显。
- 精确模型、通配符、映射和歧义处理。
- API Key 平台授权过滤。
- 账号旧 `model_mapping` 不再影响平台账号选择。
- 同 Platform 多账号负载均衡和失败切换。
- Chat Completions 与 Responses 使用平台统一端点。
- `/v1/models` 只返回授权 Platform 的精确请求模型。
- Antigravity、Grok、Bedrock 内置协议映射不回归。
- 套餐优先、套餐切换、余额回退和用量归属不回归。

### 前端

- Platform 表单支持统一端点、白名单和映射。
- Platform 编辑时完整回显。
- 账号创建、编辑和批量编辑不再显示普通模型配置。
- 类型检查、Lint、组件测试和生产构建通过。

### 部署验收

- `/v1/models` 返回当前 Key 授权平台模型。
- `/v1/chat/completions` 和 `/v1/responses` 按平台端点正确响应。
- 请求模型与上游模型映射正确。
- 使用记录包含实际 Platform、账号和模型链。
- 套餐或余额实际扣费与记录一致。

## 风险

- 账号模型映射当前分散在普通 Gateway、OpenAI Gateway、模型列表和特殊适配器，必须逐入口审计。
- 统一端点会有意扩大旧逐模型端点配置的适用范围。
- 管理员误把能力不同的账号加入同一 Platform 时，系统不会提前发现。
- 特殊适配器的技术映射若被误当作账号配置删除，会造成协议回归。

## 不在本次范围

- 不实现账号上游模型自动同步或能力校验。
- 不提供账号级模型覆盖。
- 不改变套餐、余额、倍率和模型基础定价。
- 不重写 GatewayRuntime 的 OAuth、调度或失败切换算法。
- 不物理删除账号 JSON 中的旧模型配置。
- 不把协议专项配置自动合并进普通平台模型白名单。
